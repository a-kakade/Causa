## 3. Existing code that should be reused

- **`scripts/profile_olist.py`**'s pure helper functions (`validate_candidate_key`,
  `check_foreign_key`, `compute_relationship_cardinality`, `validate_date_column`) are
  well-factored, independently unit-tested, and directly reusable in a future Step 2
  cleaning/transformation layer — they take DataFrames in, return dicts out, no
  hidden I/O.
- **`scripts/kpi_temporal_eda.py`**'s `build_order_fact()` function is a reasonable
  starting point for the canonical order-grain fact table Step 2 will need, though it
  currently bakes in a business decision (last review by answer timestamp) that Step 2
  should make an explicit, named parameter rather than a hardcoded default.
- The **revenue-reconciliation logic** (`revenue_reconciliation()` in
  `kpi_temporal_eda.py`) and the **fan-out demonstration**
  (`join_fanout_demo()` in `join_driver_anomaly_eda.py`) are both genuinely useful,
  correct, and worth carrying into Step 2 as-is or lightly adapted.

## 4. Duplicated functionality

- **Date/FK validation logic is implemented twice**, once in `profile_olist.py`
  (`validate_date_column`, `check_foreign_key`) and again, independently, in this
  audit's new `scripts/audit_raw_data.py` (by design, per this task's requirement
  to verify rather than trust). The two implementations differ slightly (this
  audit's version also reports raw-vs-parsed-null distinction and BOM/delimiter
  checks that the original did not). **Recommendation for Step 2: consolidate into
  one shared validation module** (e.g. `scripts/lib/validation.py`) rather than
  maintaining two parallel implementations going forward.
- **Language detection is implemented twice with materially different methods**:
  `text_and_entity_eda.py` uses a hand-rolled Portuguese/English stopword+diacritic
  heuristic; this audit's `audit_raw_data.py` uses `langdetect` (a real, if
  imperfect, statistical detector). **They disagree substantially** — the heuristic
  reported 91.8% "pt-likely"; the real detector reports 87.3% `pt` with a long,
  implausible tail (Italian 4.1%, Slovak 1.0%, Romanian 0.9%, etc.) that is almost
  certainly short-text misclassification, not genuine multilingual content. This
  divergence itself is a finding, not just redundancy — see `DATA_FOUNDATION_REPORT.md`
  §F.
- **Revenue/order-fact construction logic** is duplicated in spirit between
  `kpi_temporal_eda.py`'s `build_order_fact()` and the relationship/reconciliation
  checks in `join_driver_anomaly_eda.py` and `audit_raw_data.py` — each recomputes
  order-item aggregation independently. None of this is wrong (independent
  recomputation is exactly what this Step 1 asked for), but it means there is
  **no single canonical implementation yet** of "aggregate order_items to order
  grain" — that consolidation is Step 2 work.

## 5. Cross-check: prior EDA claims vs. this audit's independent recomputation

Every headline number in `docs/DATA_QUALITY_REPORT.md` and `docs/EDA_REPORT.md` was
recomputed from scratch by `scripts/audit_raw_data.py` (a new script that does not
import or call the prior scripts). Result: **all cross-checked numbers matched
exactly** — row counts (99,441 orders / 112,650 items / 103,886 payments / 99,224
reviews / 32,951 products / 3,095 sellers / 1,000,163 geolocation rows), FK match
rates, the 814 duplicate `review_id`s, the 96,096 distinct `customer_unique_id`
values, and the temporal edge-collapse pattern (329 orders in all of 2016, volume
falling to 16 and 4 orders in Sept/Oct 2018). No discrepancy was found between the
two independent computations. This is reported as a genuine finding (the raw data
and both codebases are internally consistent), not assumed.

One thing the prior EDA did **not** check that this audit did: **file-level
encoding/BOM/delimiter verification**. Finding: `product_category_name_translation.csv`
has a UTF-8 BOM (`\xef\xbb\xbf`) at the start of its header row; the other 8 files do
not. Verified this does **not** currently break `pandas.read_csv(..., encoding="utf-8")`
in this environment (pandas 2.3.3 strips it automatically), but it is a genuine
inconsistency across the file set that a naive line-based parser (not pandas) could
mishandle. See `DATA_FOUNDATION_REPORT.md` for severity.

## 6. Missing components

- **No configuration file** (no `pyproject.toml`, `.env`, `config.yaml`) — file
  paths are hardcoded relative to `Path(__file__).resolve().parents[1]` in every
  script. Fine for a single-developer hackathon milestone; would need externalizing
  before multiple environments (dev/staging) are introduced.
- **No CI** (no `.github/workflows/`, no pre-commit config) — tests exist
  (`test_profile_olist.py`) but nothing runs them automatically.
- **No dependency lockfile** — `requirements.txt` uses `>=` minimums only, so a
  fresh install is not guaranteed to reproduce today's exact package versions
  (this matters concretely for `langdetect`, whose results can shift across
  versions even with a fixed seed).
- **No integration tests against the real data** — `test_profile_olist.py` only
  tests pure functions on synthetic frames; there is no automated check that, e.g.,
  "orders.csv still has 99,441 rows" or "no new orphan FKs appeared" if the raw data
  is ever refreshed. This audit's `scripts/audit_raw_data.py` could be adapted into
  such a check (e.g., a pytest wrapper asserting against `reports/raw_data_profile.json`
  thresholds) in a future step.
- **No data versioning** — `archive.zip`'s provenance (exact Kaggle download date,
  checksum) is not recorded anywhere. If the Kaggle dataset is ever updated
  upstream, there is currently no way to detect that this repo's copy has drifted.

## 7. Potential technical debt

- Business decisions are currently **embedded as defaults inside analysis
  scripts** rather than declared as explicit, named configuration — e.g., the
  review-dedup rule ("last review by answer timestamp") is hardcoded in
  `kpi_temporal_eda.py`'s `build_order_fact()` rather than being a documented,
  overridable parameter. This is exactly the kind of silent decision Step 1's
  brief warns against; it should become an explicit, named choice in Step 2, not
  carried forward implicitly.
- `docs/EDA_REPORT.md` already **prescribes a final analytical time window**
  (2017-01 through 2018-08) as though decided. This Step 1 explicitly says not to
  decide the final window yet — treat that prior recommendation as a
  **candidate**, re-surfaced with fresh evidence in `DATA_FOUNDATION_REPORT.md`
  §E, not as a settled decision to inherit uncritically.
- `.venv/` (424MB) and `archive.zip` (43MB) are both present in the working tree;
  both are correctly gitignored, but neither is a small repository footprint —
  worth confirming the hackathon submission process doesn't expect a slim repo
  (e.g., via a fresh-clone `pip install -r requirements.txt` reproducibility
  check, which was not tested in this audit).
